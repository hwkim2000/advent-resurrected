# Requirements Document

## Introduction

Voice input lets a player in Haunted mode hold a microphone button with a mouse or pen, tap it on a touch screen, or use a keyboard shortcut, speak an English command, and have the recognized sentence go through exactly the same path as a typed line: the same submit queue, input echo, history, AI parser and fallback rules. The speech-to-text provider for this spec is the browser Web Speech API (`SpeechRecognition` or `webkitSpeechRecognition`), reached through a provider-agnostic interface so that a hosted speech-to-text service behind the Worker can replace it later without touching the matcher, the session logic or the UI.

Speech engines mis-transcribe the game's magic words (for example "zizzy" for XYZZY, "plover's" for PLOVER, "fee fi fo fum" for FEE FIE FOE FOO). Voice transcripts therefore pass through a deterministic magic-word matcher (alias lists plus bounded edit distance). The matcher applies to voice transcripts only; typed input keeps using the exact classic parser.

The product steering says "XYZZY must be spoken aloud (in Haunted mode)". This spec reads that as a Haunted-mode puzzle rule: a typed XYZZY is answered by the narrator with a hint to say it aloud, while a spoken XYZZY reaches the engine unchanged. The rule applies only while voice input is usable, and it is a hint, not a wall: the narrator deflects a typed XYZZY only once per game, and the next typed XYZZY in that game works normally, so that the 430-point game stays completable without a microphone and for players who cannot or will not speak. The once-per-game flag survives a page reload (Requirement 12). This was decided by the project owner (see "Open Questions and Decisions" at the end of this document).

Voice input is an enhancement. Typing keeps working in every mode and in every failure case (unsupported browser, denied permission, no microphone, insecure context, network error). 1976 mode loads no voice code and never touches the microphone. Speech synthesis (voice output) is not part of this spec.

Findings from the existing code and documents that shape these requirements:

- `GameController.submit(raw)` queues lines FIFO, echoes the line at its turn, optionally resolves it asynchronously through the `InputResolver` (only when the Game_Mode is `haunted`, the prompt kind is `command` and the phase is `ready`), then calls `deliver`, which runs `ExtensionHooks.transformInput` and `step`. The controller has no notion of where a line came from, so a spoken line and a typed line are indistinguishable. Requirement 13 adds the origin.
- `classifyInput` in `src/parser/eligibility.ts` skips the AI for numeric or blank lines and for lines that `isClassicCommandText` accepts. `isClassicCommandText` lives in `src/shared` (not in `src/parser`), needs the running game's `zzword` and `oldstyle` values, and reaches the Voice_Layer as an injected predicate `isClassicCommand(text)` bound to the running game and supplied through the voice port by the controller or `src/main.ts`, so that the Voice_Layer never reads engine state and never imports `src/parser`. Classic commands therefore never reach the AI, and the Meta_Commands (`QUIT`, `SAVE`, `RESUME`, `SEED`, `WASTE`) can never be produced by the AI (`src/shared/meta-commands.ts`).
- `ExtensionHooks.transformInput` is synchronous and cannot swallow a line. The XYZZY rule needs a veto that skips `step`, so Requirement 13 adds an input gate to the hook registry.
- `src/main.ts` wires `createHauntedStartLoader` from `src/ai-loader.ts`: the AI chunk loads through a dynamic `import()` the first time a Haunted game starts and never in 1976 mode. Voice follows the same rule. `tests/ui-layering.test.ts` currently forbids any import of `src/voice` from `src/ui` and `src/main.ts`, including dynamic ones; Requirement 18 changes that rule to the one that already exists for `src/parser`.
- `LineKind` is `original | input | translation | notice | narrator | boot`, and the autosave persists the kinds `original`, `input`, `notice`, `narrator` and `translation`. Voice status text is therefore not written to the transcript; it lives in its own status element.
- In the classic parser each word matches on its first 5 characters, and a line has at most two words. `FEE`, `FIE`, `FOE` and `FOO` are separate lines in the upstream win430 replay (`fee`, `fie`, `foe`, `foo`), so a spoken "fee fie foe foo" must be split into four lines. `XYZZY` and `PLUGH` are shortcuts used by the upstream replays; the sequence `FEE FIE FOE FOO` is needed for the eggs treasure of the 430-point game.
- `public/_headers` sets a same-origin Content-Security-Policy and has no `Permissions-Policy`. The README says a later spec may add one. `scripts/check-dist.ts` does not inspect `_headers` today and checks privacy statements (a) to (d) on the credits bundle.
- The ai-parser privacy statement already says that "the line you typed or spoke" is sent to Cloudflare Workers AI when it is not a classic command. Spoken sentences therefore reach the AI parser's privacy statement unchanged, and voice adds a second, separate disclosure: the audio itself goes to the browser's speech service.

Facts checked against current documentation, and facts that could not be checked:

- Checked (MDN, Web Speech API): by default the recognition service is server-based, so audio is sent to a web service and recognition does not work offline; the API defines `lang`, `continuous`, `interimResults` and `maxAlternatives`; error values include `not-allowed`, `service-not-allowed`, `audio-capture`, `network`, `no-speech`, `aborted` and `language-not-supported`; `phrases` (contextual biasing) and `processLocally` exist but have limited availability; `Permissions-Policy: microphone` has a default allowlist of `self` and is documented for `getUserMedia`.
- Not verified: whether the `microphone` Permissions-Policy directive also governs `SpeechRecognition.start()` in every browser. Community reports say `microphone=()` produces a `not-allowed` error in Chrome; no specification text was found. `microphone=(self)` is safe under both readings and is the value this spec uses.
- Not verified: whether Content-Security-Policy `connect-src` affects `SpeechRecognition`. MDN describes `connect-src` as limiting URLs loaded through script interfaces such as fetch, XHR and WebSocket; the recognition connection is made by the browser, not by page script, and no documentation was found saying otherwise. The CSP stays unchanged; the manual checklist (Requirement 16) verifies this on the deployed site in Chrome, Edge and Safari.
- Not verified: which company processes the audio in each browser (reports say Google for Chrome and Apple for Safari; Edge was not checked), whether Safari or iOS asks for permission on every start, whether Brave and other Chromium derivatives return `network` immediately, and whether `SpeechRecognition.start()` accepts the user activation of a touch `click` on every touch browser. Touch recognition therefore starts on the `click` that follows a touch press (a guaranteed user activation), never on `pointerdown`, which is not a user activation for touch input; mouse and pen keep starting on `pointerdown`. The Mic_Button is shown wherever `SpeechRecognition` or `webkitSpeechRecognition` exists (browser-compat-data lists desktop Firefox 160, so a Firefox build that ships the API shows it) and no browser is special-cased; a `start()` that fails with `not-allowed`, `service-not-allowed` or an unsupported condition (`language-not-supported`, or `start` throwing) hides the button for the rest of the page lifetime. Requirement 14 therefore words the disclosure as "the maker of your browser" without naming a company, and Requirement 16 puts these items on the real-device checklist.

## Glossary

- **Voice_Layer**: The code in `src/voice` (provider interface, Web Speech adapter, session controller, transcript cleaning, magic-word matcher, yes/no mapper). It imports nothing from `src/ui` and nothing from `src/parser`.
- **Mic_Button**: The `<button id="mic">` in the input line, hidden by default in `index.html`, bound to the Voice_Layer by a small DOM module in `src/ui/dom` through a structurally typed port.
- **Voice_Disclosure**: The always-visible text element `<p id="mic-disclosure">` next to the Mic_Button that states where speech goes (Requirement 14). It is static text in `index.html`, hidden by default, shown and hidden together with the Mic_Button by the same DOM module, and it is not part of the transcript. Its exact text is the Voice_Disclosure_Text.
- **Voice_Disclosure_Text**: Exactly `Speech is processed by your browser's speech service (from the maker of your browser). This game stores no audio.` It is defined once, in a single exported constant (module location chosen by design); `index.html`, the tests and `scripts/check-dist.ts` all equal that constant.
- **Voice_Status**: The visible one-line element next to the input line that shows listening state, the live preview and calm messages. It carries `aria-hidden="true"`, is not part of the transcript and is never persisted; its messages (but not `LISTENING...` or the preview) are mirrored once to the Voice_Live_Region.
- **Voice_Live_Region**: A polite, atomic `aria-live` region, separate from `#live` and `#live-interpreted`, empty in Mode_1976, that announces the calm messages and `Heard: ` followed by the Cleaned_Text after a result. It announces nothing when listening starts, and it never carries the Voice_Disclosure or the Deflection_Line.
- **Speech_Provider**: The provider-agnostic interface in `src/voice` through which the Voice_Layer starts, stops and aborts recognition and receives interim text, final alternatives and normalized errors.
- **Web_Speech_Adapter**: The only module that references `SpeechRecognition` or `webkitSpeechRecognition`; it implements Speech_Provider.
- **Voice_Error_Code**: One of `denied`, `no-device`, `network`, `no-speech`, `unsupported-language`, `aborted`, `other`.
- **Voice_Session**: One recognition run from a start request to its end event.
- **Hold_Mode**: A Voice_Session in which the player held the Mic_Button with a mouse or pen pointer, or held the Alt+M shortcut, for at least MIN_HOLD_MS; releasing stops the session. Touch input never uses Hold_Mode.
- **Latch_Mode**: A Voice_Session that keeps listening after a mouse or pen press or an Alt+M press shorter than MIN_HOLD_MS, after keyboard activation (Enter or Space) of the Mic_Button, or after a Touch_Click, until a final result, MAX_LISTEN_MS, or the next activation.
- **Touch_Press**: A pointer press on the Mic_Button whose `pointerType` is `touch`. A Touch_Press never starts, stops or aborts a Voice_Session by itself; only the Touch_Click that follows it does.
- **Touch_Click**: The `click` event (`detail` greater than 0) that follows a Touch_Press on the Mic_Button. It is the only touch activation (a guaranteed user activation) and toggles Latch_Mode: the first Touch_Click starts a Voice_Session, the next calls `stop`. No MIN_HOLD_MS decision applies to touch.
- **Voice_Availability**: The state of the Voice_Layer, one of: `Unsupported` (no usable API or insecure context; hidden for the page lifetime), `Ready` (button shown and enabled), `Busy` (a Voice_Session is running), `Suspended` (hidden because the running game is a Mode_1976 game) and `Unavailable` (hidden after a fatal error, a denied permission or an unusable start). `Unavailable` caused by a Requirement 7 runtime error (the error codes `denied`, `no-device` and `unsupported-language`, a `start` call that throws, or three consecutive failures) or by a failed recognition-object construction lasts for the rest of the page lifetime (the "page session"); the one exception is `Unavailable` caused by a permission-based `denied` at detection (Requirement 2.4), which a later permission change to `granted` or `prompt` reverses (Requirement 2.5). `Suspended` takes precedence over `Ready` (Requirement 1.11).
- **Voice_Usable**: Voice_Availability is `Ready` or `Busy`.
- **Spoken_Text**: A string produced by a Speech_Provider (an interim text, or one alternative of a final result).
- **Cleaned_Text**: Spoken_Text after the cleaning in Requirement 8.
- **Alternative**: One hypothesis of a final result, in provider order (best first).
- **Magic_Word**: One of XYZZY, PLUGH, PLOVER, FEE, FIE, FOE, FOO. The sequence FEE FIE FOE FOO is the Magic_Sequence.
- **Magic_Alias_Table**: The fixed table in `src/voice` that maps spoken spellings (aliases) to Magic_Words. It is part of the source, not generated at run time.
- **Magic_Match**: The result of the matcher: an ordered list of 1 to 4 canonical Magic_Word commands, the index of the Alternative that produced it, and the tier (`alias` or `edit`) that matched.
- **Stop_List**: A fixed list of at least 30 ordinary English words that the edit-distance tier must never map to a Magic_Word (for example `plush`, `fizzy`, `dizzy`, `fuzzy`, `clover`, `lover`, `plugs`).
- **Input_Origin**: `typed` or `spoken`, the source of a submitted line. It travels with the queued line until delivery (Requirement 13.1) and is never stored (Requirement 14.2).
- **isClassicCommand**: The predicate `isClassicCommand(text): boolean` injected into the Voice_Layer through the voice port. It is bound to the running game (its `zzword` and `oldstyle`) and wraps `isClassicCommandText` of `src/shared`, so that the Voice_Layer never reads engine state and never imports `src/parser`.
- **Input_Gate**: A synchronous hook in the ExtensionHooks registry that may veto the delivery of an engine-bound command to `step` and replace it with narrator lines.
- **Spoken_Word_Rule**: The rule in Requirement 12 that a typed XYZZY is deflected in Haunted mode while Voice_Usable.
- **Deflection**: A veto by the Spoken_Word_Rule: the typed XYZZY is echoed, `step` is not called, and the Deflection_Line is shown.
- **DEFLECTION_LIMIT**: 1.
- **Deflection_Count**: The integer number of Deflections in the current game, from 0 to DEFLECTION_LIMIT. It is per-game UI state owned by the GameController, not engine state: it is not part of `GameState`, not part of `serialize` output and not part of an in-game `SAVE` file. It is persisted only in the Autosave_Voice_Field.
- **Autosave_Voice_Field**: The optional field `ui` of the autosave record, shaped `{ "deflections": <integer> }` (Requirement 13.11). The record version stays `1`.
- **Deflection_Line**: The one fixed Narrator_Line of Requirement 12.4, exactly `SAY IT ALOUD. HOLD THE MIC OR ALT+M. TYPE XYZZY AGAIN IF YOU MUST.`
- **Game_Mode**, **Haunted_Mode**, **Mode_1976**, **Player_Text**, **Classic_Command**, **Meta_Command**, **Translation_Line**, **Original_Text**, **Game_Vocabulary**, **AI_Parser**: As defined in the ai-parser and crt-terminal-ui specs. In particular, Meta_Command means exactly `QUIT`, `SAVE`, `RESUME`, `SEED` and `WASTE` and their vocabulary spellings.
- **Narrator_Line**: A line of kind `narrator`, shown after (never instead of) Original_Text; here also used for the Deflection_Line, which has no Original_Text because `step` is not called.
- **Constants** (one module `src/voice/config.ts`): MIN_HOLD_MS = 250; MAX_LISTEN_MS = 10000; RESULT_WAIT_MS = 3000; STATUS_CLEAR_MS = 4000; PREVIEW_MAX_CHARS = 80; MAX_ALTERNATIVES = 5; MAGIC_ALTERNATIVES_CHECKED = 3; MAGIC_TOP_TOKEN_LIMIT = 4; REPEATED_ERRORS_BEFORE_HIDE = 3; SPOKEN_TEXT_MAX_CHARS = 200 (equal to `TEXT_MAX_CHARS`); DEFLECTION_LIMIT = 1.

## Requirements

### Requirement 1: Mode gating and lazy loading

**User Story:** As a player of 1976 mode, I want no voice code to run and no microphone to be touched, so that the original experience stays pure and private.

#### Acceptance Criteria

1. WHILE the Game_Mode of the running game is Mode_1976, THE System SHALL make zero calls to the `SpeechRecognition` or `webkitSpeechRecognition` constructors, zero calls to `navigator.mediaDevices.getUserMedia`, zero calls to `navigator.permissions.query`, and zero network requests for the Voice_Layer chunk, from the start of that game until the next game starts.
2. WHILE the Game_Mode of the running game is Mode_1976, THE Mic_Button and THE Voice_Disclosure SHALL each carry the `hidden` attribute (also before the Voice_Layer has loaded, in every Game_Mode), THE Voice_Status SHALL have empty `textContent`, and THE Voice_Live_Region SHALL have empty `textContent`.
3. WHEN a game starts with Game_Mode Haunted_Mode and the Voice_Layer is not loaded and no load is pending, THE System SHALL start loading the Voice_Layer through a dynamic `import()` in `src/main.ts`, and THE System SHALL NOT import the Voice_Layer by any other path. THE System SHALL run at most one load at a time and SHALL keep a successfully loaded Voice_Layer for the rest of the page lifetime without loading it again.
4. WHEN a game starts with Game_Mode Mode_1976 and the Voice_Layer is loaded, THE System SHALL abort any running Voice_Session without submitting a line, hide the Mic_Button and the Voice_Disclosure, clear the Voice_Status and the Voice_Live_Region, set Voice_Availability to `Suspended`, and remove the Input_Gate of Requirement 12, all before the first prompt of that game is shown.
5. WHEN a game starts with Game_Mode Haunted_Mode and Voice_Availability is `Suspended`, THE System SHALL set Voice_Availability to `Ready`, show the Mic_Button and the Voice_Disclosure, and register the Input_Gate of Requirement 12 again, unless detection under Requirement 2 had set `Unsupported` or `Unavailable`, in which case Voice_Availability SHALL stay unchanged and the Mic_Button and the Voice_Disclosure SHALL stay hidden. Detection under Requirement 2 SHALL NOT run again.
6. WHEN an autosaved game is restored at page load, THE System SHALL apply this requirement using the restored game's own Game_Mode, not the selected mode: a restored Mode_1976 game SHALL trigger no load, and a restored Haunted_Mode game SHALL trigger the load of criterion 3.
7. WHEN the player changes the selected mode during a running game, THE System SHALL leave the Voice_Availability, the hidden state of the Mic_Button and the Voice_Disclosure, and the loaded or unloaded state of the Voice_Layer unchanged, SHALL trigger no load and no abort, and SHALL apply the new mode only when the next game starts.
8. IF the load of the Voice_Layer fails (the `import()` rejects), THEN THE System SHALL log one console entry that contains no Spoken_Text, show no message in the Voice_Status, the Voice_Live_Region or the transcript, keep the Mic_Button and the Voice_Disclosure hidden, leave typed input unchanged, and treat the Voice_Layer as not loaded, so that the next game start with Game_Mode Haunted_Mode tries criterion 3 again.
9. THE System SHALL show the first prompt and enable the input element without waiting for the Voice_Layer load to settle: WHILE the `import()` promise is pending (including when it never settles), typed lines SHALL be accepted and processed.
10. IF a game with Game_Mode Mode_1976 starts while the Voice_Layer load of criterion 3 is pending, THEN THE System SHALL, when the load resolves, leave the Voice_Layer in `Suspended`: it SHALL make none of the calls named in criterion 1, keep the Mic_Button and the Voice_Disclosure hidden, and register no Input_Gate.
11. WHILE Voice_Availability is `Suspended`, THE Voice_Layer SHALL ignore every microphone permission change, so that Voice_Availability stays `Suspended` and the Mic_Button and the Voice_Disclosure stay hidden (this takes precedence over Requirement 2.5).

### Requirement 2: Feature detection and hiding the microphone button

**User Story:** As a player on a browser without speech recognition, I want the game to simply have no mic button, so that nothing looks broken.

#### Acceptance Criteria

1. WHEN the Voice_Layer initializes, THE Voice_Layer SHALL, IF `window.isSecureContext` is not `true` OR neither `window.SpeechRecognition` nor `window.webkitSpeechRecognition` has `typeof` equal to `"function"`, set Voice_Availability to `Unsupported` and keep the Mic_Button and the Voice_Disclosure hidden.
2. WHILE Voice_Availability is `Unsupported`, THE Voice_Layer SHALL make zero calls to the recognition constructors, `navigator.permissions.query` and `navigator.mediaDevices.getUserMedia`, keep the Mic_Button and the Voice_Disclosure hidden, leave the Voice_Status empty, write no line to the transcript, and write no message to the Voice_Live_Region.
3. IF constructing the recognition object during initialization throws, THEN THE Voice_Layer SHALL set Voice_Availability to `Unavailable`, hide the Mic_Button and the Voice_Disclosure, show no message to the player, and log only the Voice_Error_Code `other` to the console.
4. WHERE `navigator.permissions.query({ name: "microphone" })` is supported and its result has the state `denied`, THE Voice_Layer SHALL set Voice_Availability to `Unavailable`, hide the Mic_Button and the Voice_Disclosure, and show no message.
5. WHERE the permission state changes from `denied` to `granted` or `prompt`, IF Voice_Availability is `Unavailable` because of criterion 4 (not because of criterion 3 or a Requirement 7 error), THEN THE Voice_Layer SHALL set Voice_Availability to `Ready` (or to `Suspended` if the running game's Game_Mode is Mode_1976), and, when `Ready`, show the Mic_Button and the Voice_Disclosure without a message.
6. IF the permission query throws, rejects, or does not support the name `microphone`, THEN THE Voice_Layer SHALL ignore the result, keep the current Voice_Availability, and show no message.
7. THE Voice_Layer SHALL obtain microphone permission only through the Speech_Provider `start` call made in the event-handler task of a player gesture (Requirement 4.1), SHALL make zero calls to `navigator.mediaDevices.getUserMedia`, and SHALL NOT call `start` during initialization.
8. WHILE the Mic_Button or the Voice_Disclosure is hidden, THE element SHALL carry the `hidden` attribute, SHALL be absent from the tab order, SHALL be absent from the accessibility tree and SHALL occupy no layout space (computed `display` equal to `none`).
9. WHEN the Mic_Button or the Voice_Disclosure becomes hidden or shown, THE input element SHALL keep `document.activeElement`, `value`, `selectionStart` and `selectionEnd` unchanged.
10. WHILE Voice_Availability is `Unsupported`, `Unavailable` or `Suspended`, THE System SHALL behave for typed input exactly as it does when the Voice_Layer is absent: the same queue, echo, history, AI_Parser and fallback behavior, and no Deflection of a typed XYZZY (Requirement 12).
11. WHEN detection under criteria 1, 3 and 4 finds no reason to set `Unsupported` or `Unavailable` and the running game's Game_Mode is Haunted_Mode, THE Voice_Layer SHALL set Voice_Availability to `Ready` and show the Mic_Button and the Voice_Disclosure, without waiting for the permission query to settle.
12. WHEN a Haunted_Mode game starts and detection already ran during this page load, THE Voice_Layer SHALL reuse the earlier result and SHALL NOT construct a recognition object or call `navigator.permissions.query` again.
13. THE Voice_Layer SHALL decide `Unsupported` by the feature test of criterion 1 only, without reading the user-agent string or a browser name, so that every browser that exposes `SpeechRecognition` or `webkitSpeechRecognition` in a secure context (Firefox builds that ship the API included) shows the Mic_Button and the Voice_Disclosure under criterion 11, and every browser without the API shows neither.
14. IF a Voice_Session ends with the Voice_Error_Code `denied` (the provider errors `not-allowed` and `service-not-allowed`) or `unsupported-language` (the provider error `language-not-supported`), OR IF the Speech_Provider `start` call throws (including a synchronous throw on the first activation of the page lifetime), THEN THE Voice_Layer SHALL set Voice_Availability to `Unavailable` for the rest of the page lifetime, hide the Mic_Button and the Voice_Disclosure, show only the calm Voice_Status message of Requirement 7.1, 7.2 or 7.17, and leave typed input fully working; this applies in every browser, including a browser that exposes the API but denies it or cannot run it (for example a Firefox with the API and a denied permission).

### Requirement 3: Provider-agnostic speech input interface

**User Story:** As a developer, I want the speech engine behind an interface, so that a hosted speech-to-text service can replace the browser API later.

#### Acceptance Criteria

1. THE Voice_Layer SHALL define a Speech_Provider interface with these operations: `isSupported()` returning a boolean, `start(options)` where every field of `options` is optional, `stop()` and `abort()`, and these callbacks: `onStart()`, `onInterim(text)` with a string, `onFinal(alternatives)` with an array of 1 to MAX_ALTERNATIVES strings in provider order (best first), `onError(code)` with a Voice_Error_Code, and `onEnd()`.
2. THE Speech_Provider interface SHALL NOT expose any `SpeechRecognition`, `SpeechRecognitionEvent` or `SpeechRecognitionResult` type or error string.
3. THE Web_Speech_Adapter SHALL be the only module under `src` whose code (excluding comments and test files) contains an identifier that begins with `SpeechRecognition` or equals `webkitSpeechRecognition`; a test SHALL scan every other file under `src` and find zero matches.
4. THE Web_Speech_Adapter SHALL map the error strings `not-allowed` and `service-not-allowed` to `denied`, `audio-capture` to `no-device`, `network` to `network`, `no-speech` to `no-speech`, `language-not-supported` to `unsupported-language`, `aborted` to `aborted`, and every other value, including a missing or non-string value, to `other`.
5. THE Web_Speech_Adapter SHALL set `lang` to `en-US`, `continuous` to `false`, `interimResults` to `true` and `maxAlternatives` to MAX_ALTERNATIVES on every recognition object, and SHALL ignore any `options` field that tries to change these values.
6. WHEN an event arrives from a recognition object whose Voice_Session has been aborted or has ended, THE Web_Speech_Adapter SHALL ignore the event and SHALL call no callback for it.
7. WHERE the browser supports `phrases` (contextual biasing), THE Web_Speech_Adapter SHALL offer the words XYZZY, PLUGH, PLOVER, FEE, FIE, FOE and FOO as phrases, and SHALL ignore a `phrases-not-supported` error or a thrown exception from that setting, so that the Voice_Session starts and the error mapping of criterion 4 is not triggered.
8. THE session controller, the matcher, the cleaning function and the UI port SHALL depend only on the Speech_Provider interface, so that a second implementation can replace the Web_Speech_Adapter without a change to those modules; a test using a fake Speech_Provider SHALL drive a complete Voice_Session through the session controller without the Web_Speech_Adapter being imported.
9. THE Speech_Provider SHALL deliver the callbacks of one Voice_Session in this order: `onStart` at most once, then zero or more `onInterim`, then `onFinal` at most once, then `onError` at most once, then `onEnd` exactly once as the last callback, and SHALL call no callback of that Voice_Session after `onEnd`.
10. IF the recognition service ends a Voice_Session with no result and no error, OR IF a final result contains zero alternatives, THEN THE Web_Speech_Adapter SHALL call `onError('no-speech')` followed by `onEnd()` and SHALL NOT call `onFinal`.
11. IF a final result contains more than MAX_ALTERNATIVES alternatives, THEN THE Web_Speech_Adapter SHALL pass only the first MAX_ALTERNATIVES alternatives, in provider order, to `onFinal`.
12. THE operations `isSupported()`, `stop()` and `abort()` SHALL NOT throw: `isSupported()` SHALL have no side effects and SHALL NOT access the microphone, and `stop()` and `abort()` called while no Voice_Session is running SHALL do nothing.
13. IF `start(options)` is called while a Voice_Session is running, THEN THE Speech_Provider SHALL throw an exception, SHALL leave the running Voice_Session unchanged, and SHALL call no callback for the rejected call.

### Requirement 4: Push-to-talk interaction

**User Story:** As a player, I want to hold a button or key to talk and let go to send, so that the game only listens when I mean it to.

#### Acceptance Criteria

1. WHEN the primary button of a primary pointer whose `pointerType` is `mouse` or `pen` is pressed on the Mic_Button while Voice_Availability is `Ready` and the Mic_Button is not disabled under criterion 14, THE Voice_Layer SHALL call the Speech_Provider `start` in the same event-handler task as the `pointerdown`, including the very first press of the page lifetime (no preliminary notice, confirmation or second press is required), and SHALL record the press time for the MIN_HOLD_MS decision.
2. WHEN the mouse or pen pointer of criterion 1 is released and the time from the `pointerdown` to the `pointerup` is at least MIN_HOLD_MS, THE Voice_Layer SHALL end the Voice_Session as Hold_Mode by calling `stop`, and SHALL still process a final result that arrives within RESULT_WAIT_MS after the `stop` call (Requirement 5.2 applies after that).
3. WHEN the mouse or pen pointer of criterion 1 is released and the time from the `pointerdown` to the `pointerup` is less than MIN_HOLD_MS, THE Voice_Layer SHALL keep listening as Latch_Mode and SHALL NOT call `stop` because of the release.
4. WHILE a Voice_Session is in Latch_Mode, WHEN the Mic_Button is pressed by a mouse or pen pointer, activated by keyboard, or activated by a Touch_Click, THE Voice_Layer SHALL call `stop` and SHALL treat that activation as a stop request and not as a start request; the `pointerup` of a mouse or pen stop-press, and the `pointerdown` and `pointerup` of the Touch_Press of a Touch_Click stop-activation, SHALL NOT start a Voice_Session, call `stop` or `abort` again, or change the mode.
5. WHEN a Voice_Session is running and the browser reports `pointercancel`, or `lostpointercapture` without a preceding `pointerup`, for the mouse or pen press that is holding the session (Hold_Mode press only), OR reports `window` `blur`, `visibilitychange` to hidden or `pagehide`, OR the Escape key is pressed, THE Voice_Layer SHALL call `abort`, SHALL submit no line for that Voice_Session, and SHALL show no message in the Voice_Status. A `pointercancel` or `lostpointercapture` of a Touch_Press SHALL be ignored, because a touch session is never held. WHILE no Voice_Session is running, THE Voice_Layer SHALL NOT act on the Escape key and SHALL NOT call `preventDefault` for it.
6. WHEN the Mic_Button has keyboard focus and is activated by the Enter key or the Space key (a `click` event that has `detail` equal to 0), THE Voice_Layer SHALL toggle Latch_Mode without applying MIN_HOLD_MS: while Voice_Availability is `Ready` and the Mic_Button is not disabled, the activation starts a Voice_Session in Latch_Mode, and while a Voice_Session is running, the next activation calls `stop`.
7. WHEN the key combination Alt+M is pressed (key code `KeyM`, `altKey` true, `ctrlKey`, `metaKey` and `shiftKey` false, `repeat` false) while Voice_Availability is `Ready` and the Mic_Button is not disabled under criterion 14, THE Voice_Layer SHALL call `start` in the same task as the `keydown`, and the Voice_Session SHALL follow the MIN_HOLD_MS rule of criteria 2 and 3 measured from that `keydown`; THE Voice_Layer SHALL call `preventDefault` on every Alt+M `keydown` (including `repeat` true) while Voice_Availability is `Ready` or `Busy`, so that no character is inserted in the input. WHILE a Voice_Session started by Alt+M is in Latch_Mode, WHEN Alt+M is pressed again, THE Voice_Layer SHALL call `stop`.
8. WHEN the M key or the Alt key is released during an Alt+M Voice_Session and the time since the Alt+M `keydown` is at least MIN_HOLD_MS, THE Voice_Layer SHALL call `stop`; WHEN it is released earlier, THE Voice_Layer SHALL keep listening as Latch_Mode.
9. WHILE a Voice_Session is running, THE Voice_Layer SHALL ignore every start request (mouse or pen pointer press, Touch_Click, keyboard activation that is not a stop under criteria 4, 6 and 18, Alt+M that is not a stop under criterion 7, and auto-repeat `keydown`): no second `start` call, no change of mode and no change of the Voice_Status.
10. FROM the `start` call until the end event of the Voice_Session (including the wait after `stop`), THE Mic_Button SHALL have `aria-pressed="true"`, and otherwise THE Mic_Button SHALL have `aria-pressed="false"`.
11. THE Mic_Button SHALL have the attribute `aria-keyshortcuts="Alt+M"` and an accessible name that contains the words "hold" and "talk" (case-insensitive, as whole words).
12. THE Mic_Button SHALL be at least 44 by 44 CSS pixels, SHALL set `touch-action: manipulation` (so that the Touch_Click is delivered reliably and a double tap on the button does not zoom the page) and `user-select: none`, and SHALL call `preventDefault` on its `contextmenu` event (so that a long press shows no context menu).
13. WHEN a pointer of any `pointerType` is pressed on the Mic_Button, OR a Touch_Click is processed, THE Mic_Button SHALL leave `document.activeElement`, the input value and the input selection unchanged, so that an on-screen keyboard is not dismissed by the press; for a Touch_Press this includes a `preventDefault` on the `pointerdown` and on any compatibility `mousedown`.
14. WHILE the game phase is not `ready`, OR the engine prompt kind is `filename`, THE Mic_Button SHALL be shown with `aria-disabled="true"` and the accessible description "Voice input is not available for this question", and no pointer press, Touch_Click, keyboard activation or Alt+M SHALL start a Voice_Session or show a message. WHEN the condition ends, THE Mic_Button SHALL drop `aria-disabled` and the description within 100 ms.
15. WHEN a `click` event on the Mic_Button follows a mouse or pen pointer press (`detail` greater than 0), THE Voice_Layer SHALL ignore it, so that one pointer press never starts and stops a Voice_Session twice. A `click` that follows a Touch_Press is a Touch_Click and is handled by criterion 18.
16. IF the mouse or pen pointer or the key is released before the Speech_Provider `onStart` callback has fired (for example while the browser permission prompt is open), THEN THE Voice_Layer SHALL apply criteria 2 and 3 to the elapsed time as usual, SHALL NOT drop the release, and SHALL start the MAX_LISTEN_MS count at `onStart`. A Touch_Click has no release decision.
17. WHEN a Touch_Press occurs on the Mic_Button (a `pointerdown` whose `pointerType` is `touch`), THE Voice_Layer SHALL NOT start, stop or abort a Voice_Session on the `pointerdown` or on the `pointerup` of that press, and SHALL NOT apply MIN_HOLD_MS to it.
18. WHEN a Touch_Click occurs on the Mic_Button, THE Voice_Layer SHALL toggle Latch_Mode without applying MIN_HOLD_MS: while Voice_Availability is `Ready` and the Mic_Button is not disabled under criterion 14, the Touch_Click SHALL call the Speech_Provider `start` in the same event-handler task as the `click` (including the first activation of the page lifetime) and start the Voice_Session in Latch_Mode; while a Voice_Session is running in Latch_Mode and `stop` has not been requested, the next Touch_Click SHALL call `stop`; in every other case the Touch_Click SHALL be ignored under criterion 9.
19. THE Voice_Layer SHALL process one touch tap as exactly one activation: the `pointerdown` and `pointerup` of its Touch_Press start and stop nothing and the Touch_Click toggles once, so that one tap never starts and stops a Voice_Session twice; a touch long press that ends in a `contextmenu` or `pointercancel` without a Touch_Click SHALL start nothing.

### Requirement 5: Recognition session lifecycle

**User Story:** As a player, I want listening to end cleanly and predictably, so that nothing keeps listening or fires late.

#### Acceptance Criteria

1. WHEN a Voice_Session has been listening for MAX_LISTEN_MS, measured from the Speech_Provider `onStart` callback of that session, THE Voice_Layer SHALL call `stop` once, whether the session is in Hold_Mode or Latch_Mode and whether or not the Mic_Button is still held.
2. WHEN `stop` is called for a Voice_Session (by release, a second activation, or criterion 1), THE Voice_Layer SHALL start a RESULT_WAIT_MS timer, and IF neither a final result nor the end event has arrived when the timer expires, THEN THE Voice_Layer SHALL call `abort`, submit no line, and show the message `NOTHING HEARD.` in the Voice_Status. A second `stop` call in the same session SHALL NOT restart the timer, and the `aborted` error code that this `abort` causes SHALL be ignored (it SHALL NOT show a message under Requirement 7.6 and SHALL NOT count toward REPEATED_ERRORS_BEFORE_HIDE).
3. WHEN the first final result of a Voice_Session arrives, THE Voice_Layer SHALL process it exactly once (passing its Alternatives to Requirements 8 to 11 and resetting the consecutive-error count of Requirement 7.7 to 0) and SHALL ignore every later final result and every later interim text of the same Voice_Session.
4. WHEN a final result arrives while the player still holds the Mic_Button or the Alt+M shortcut, THE Voice_Layer SHALL process the result immediately without waiting for the release, and the held press SHALL NOT start another Voice_Session until the pointer or key has been released and pressed again; the later release SHALL call neither `stop` nor `abort` on the ended session.
5. WHEN a new game starts (including the restore of an autosaved game), OR the running game's Game_Mode is Mode_1976, OR the game phase leaves `ready`, OR the engine prompt kind becomes `filename`, THE Voice_Layer SHALL call `abort` on any running Voice_Session, SHALL submit no line from it, SHALL show no message, SHALL clear the Voice_Status immediately, and SHALL cancel the timers of criteria 1 and 2.
6. WHEN a final result, an interim text or an error arrives after its Voice_Session was aborted or has ended, THE Voice_Layer SHALL discard it: it SHALL NOT submit a line, change the Voice_Status, change Voice_Availability, announce in the Voice_Live_Region, or count toward REPEATED_ERRORS_BEFORE_HIDE.
7. WHEN the end event of a Voice_Session arrives, THE Voice_Layer SHALL, within 100 ms, cancel the timers of criteria 1, 2 and 12, set `aria-pressed="false"` on the Mic_Button, and return Voice_Availability from `Busy` to `Ready`, unless Requirement 7, Requirement 2 or Requirement 1.4 has set it to `Unavailable`, `Unsupported` or `Suspended`, in which case that state SHALL be kept.
8. IF the Speech_Provider `start` call throws (the Voice_Layer never calls `start` while a Voice_Session is running, so a throw means that the API is not usable, for example in a browser that exposes the API but cannot run it, including a synchronous throw on the first activation of the page lifetime), THEN THE Voice_Layer SHALL handle it under Requirement 7.17 (Voice_Availability becomes `Unavailable`, never `Busy`), and SHALL keep `aria-pressed="false"` on the Mic_Button.
9. WHILE a Voice_Session is running, THE Voice_Layer SHALL NOT call `GameController.submit` or the AI_Parser for that session before its first final result is processed, and SHALL use no timer other than MIN_HOLD_MS, MAX_LISTEN_MS, RESULT_WAIT_MS, STATUS_CLEAR_MS and the 100 ms bound of criterion 7. Typed lines submitted during the session SHALL be queued and processed as without a Voice_Session (Requirements 7.11 and 8.9).
10. IF the end event of a Voice_Session arrives with no final result processed, no error code reported, and no `abort` call made by the Voice_Layer, THEN THE Voice_Layer SHALL submit no line and show `NOTHING HEARD.` in the Voice_Status.
11. IF an error code is reported for a Voice_Session after its final result was processed, THEN THE Voice_Layer SHALL ignore that error code (no message, no change of Voice_Availability, no increment of the consecutive-error count); IF an error code is reported before any final result, THEN THE Voice_Layer SHALL submit no line for that Voice_Session and apply Requirement 7.
12. IF, within MAX_LISTEN_MS plus RESULT_WAIT_MS after a start request, the Speech_Provider has reported none of `onStart`, `onError` and `onEnd`, THEN THE Voice_Layer SHALL call `abort`, submit no line, and handle the session as the error code `other` under Requirement 7. This timer can also fire when the player answers the browser permission prompt very slowly; the outcome is the calm message of Requirement 7.4, and the case is on the real-device checklist (Requirement 16.8).

### Requirement 6: Voice status and live preview

**User Story:** As a player, I want to see that the game is listening and what it heard, so that I can tell whether to speak again or type.

#### Acceptance Criteria

1. THE Voice_Status SHALL be an element outside the transcript, written only through `textContent`, and SHALL NOT be saved in the autosave, the input history or the transcript. WHILE the running game's Game_Mode is Mode_1976 OR Voice_Availability is `Unsupported`, THE Voice_Status SHALL have an empty `textContent`.
2. WHILE a Voice_Session is listening (from the Speech_Provider `onStart` callback), THE Voice_Status SHALL show exactly `LISTENING...` until the first interim text whose Cleaned_Text is not empty arrives.
3. WHEN an interim text arrives during a Voice_Session that has not been aborted and has not yet processed a final result, THE Voice_Layer SHALL clean it with the Requirement 8.1 function. IF the Cleaned_Text is not empty, THEN THE Voice_Status SHALL show `HEARD: ` followed by the first PREVIEW_MAX_CHARS (80) characters of the Cleaned_Text (a hard cut, no added ellipsis, so the maximum length is 87 characters), replacing the previous text in the same task as the interim event. IF the Cleaned_Text is empty, THEN THE Voice_Status SHALL stay unchanged.
4. THE Voice_Layer SHALL NOT write an interim text to the input element's value, to the GameController queue, to the history, to the Voice_Live_Region, to the console, or to any storage.
5. WHEN a Voice_Session has ended OR a final result has been processed, THE Voice_Layer SHALL set the `textContent` of the Voice_Status to the empty string exactly STATUS_CLEAR_MS (4000 ms) after the last change of the Voice_Status, whether that text is a preview, a result or a message of Requirements 5, 7, 8, 9 or 10. Each change of the Voice_Status SHALL restart this period. WHEN a new Voice_Session starts, THE Voice_Layer SHALL cancel any pending clear, so that no clear timer runs while Voice_Availability is `Busy`.
6. THE Voice_Layer SHALL NOT write the input element's value, `selectionStart`, `selectionEnd` or `selectionDirection`, and SHALL NOT change which element has focus, when a Voice_Session starts, runs or ends. Edits that the player types during a Voice_Session SHALL be kept.
7. WHEN a final result has been processed (a submitted line, a Magic_Match, a yes/no mapping), THE Voice_Live_Region SHALL announce `Heard: ` followed by the Cleaned_Text of the Alternative that produced the line (the Alternative named in the Magic_Match for Requirements 10.10 and 11.9, otherwise the first Alternative) exactly once, with no second announcement from Requirement 10.10 or 11.9. THE Voice_Live_Region SHALL NOT announce anything WHEN the Speech_Provider `onStart` callback fires, because a screen reader speaking while the microphone is open could be captured by the recogniser; the listening state is conveyed by the `LISTENING...` Voice_Status text and `aria-pressed="true"`.
8. WHERE the user's `prefers-reduced-motion: reduce` preference is enabled, THE Voice_Status and the Mic_Button SHALL have no running CSS animation and no CSS transition with a duration above 0 s, and the listening state SHALL still be conveyed by the `LISTENING...` text and `aria-pressed="true"`.
9. WHILE the viewport is 320 CSS pixels wide, THE input line including the Mic_Button, the Voice_Disclosure and the Voice_Status with a status text of 87 characters SHALL fit without horizontal scrolling (`scrollWidth` not greater than `clientWidth` for the document and for the input line); THE Voice_Status MAY wrap or clip its text, and its `textContent` SHALL stay unchanged.
10. WHEN a final result has been processed, THE Voice_Status SHALL show `HEARD: ` followed by the first PREVIEW_MAX_CHARS characters of the same Cleaned_Text as in criterion 7, replacing the preview, unless a message of Requirement 8.3 or 9.5 or 9.6 applies, in which case that message SHALL be shown instead.
11. WHEN a Voice_Session ends by `abort` without a message in Requirement 5 or 7 (a new game, a switch to Mode_1976, a phase change, Escape, blur, `pagehide`, or the error code `aborted`), THE Voice_Layer SHALL set the `textContent` of the Voice_Status to the empty string in the same task as the abort, without waiting for STATUS_CLEAR_MS.
12. WHEN the Voice_Status shows a message of Requirement 5.2, 5.10, 7, 8.3, 9.5 or 9.6, THE Voice_Live_Region SHALL announce the same text once. The `LISTENING...` text and the preview SHALL NOT be announced, and `Listening` SHALL NOT be announced at all.

### Requirement 7: Errors and calm degradation

**User Story:** As a player whose microphone is blocked or missing, I want a short friendly line and an unbroken game, so that I never see an alarming message.

#### Acceptance Criteria

1. WHEN a Voice_Session ends with the error code `denied` (the provider errors `not-allowed` and `service-not-allowed`), THE Voice_Layer SHALL submit no line, set Voice_Availability to `Unavailable` for the rest of the page lifetime, hide the Mic_Button and the Voice_Disclosure, and show `VOICE IS NOT AVAILABLE. KEEP TYPING.` in the Voice_Status.
2. WHEN a Voice_Session ends with the error code `no-device` or `unsupported-language` (the provider error `language-not-supported`), THE Voice_Layer SHALL submit no line, set Voice_Availability to `Unavailable` for the rest of the page lifetime, hide the Mic_Button and the Voice_Disclosure, and show `NO MICROPHONE FOUND. KEEP TYPING.` for `no-device` and `VOICE IS NOT AVAILABLE. KEEP TYPING.` for `unsupported-language`.
3. WHEN a Voice_Session ends with the error code `network`, THE Voice_Layer SHALL submit no line, show `THE VOICE SERVICE IS NOT ANSWERING. TRY AGAIN OR TYPE.` in the Voice_Status, and keep Voice_Availability `Ready` unless criterion 7 applies.
4. WHEN a Voice_Session ends with the error code `other`, THE Voice_Layer SHALL submit no line, show `VOICE TROUBLE. TYPE INSTEAD.` in the Voice_Status, and keep Voice_Availability `Ready` unless criterion 7 applies.
5. WHEN a Voice_Session ends with the error code `no-speech`, THE Voice_Layer SHALL submit no line, show `NOTHING HEARD.` in the Voice_Status, and keep Voice_Availability `Ready`.
6. WHEN a Voice_Session ends with the error code `aborted`, THE Voice_Layer SHALL submit no line, show no message, and keep Voice_Availability as it was before the session (`Ready`, or `Suspended` if the abort came from a Mode_1976 game start).
7. IF REPEATED_ERRORS_BEFORE_HIDE consecutive failed Voice_Sessions have ended (counted under criterion 13), THEN THE Voice_Layer SHALL show the message of the error code of the last session under criteria 3 or 4, set Voice_Availability to `Unavailable`, and hide the Mic_Button and the Voice_Disclosure.
8. THE Voice_Layer SHALL keep Voice_Availability `Unavailable` when it was set under criteria 1, 2, 7 or 17 (a runtime error) final for the rest of the page lifetime, SHALL NOT reverse it on a later permission-state change (Requirement 2.5) or on a later game start (Requirement 1.5), and SHALL NOT write it to storage, so that a page reload gives a new attempt. The only recoverable `Unavailable` is the permission-based one set at detection under Requirement 2.4, which Requirement 2.5 may reverse.
9. THE messages in this requirement SHALL be shown only in the Voice_Status and the Voice_Live_Region, SHALL use the same text style as every other Voice_Status text (no distinct color, no animation, no sound), and SHALL NOT be shown through `alert`, `confirm`, `prompt`, a dialog element or a transcript line, and SHALL NOT be written to the transcript, the input history or the autosave.
10. THE messages in this requirement SHALL NOT contain, in any letter case, the character sequences ERROR, FAILED, DENIED, DANGER, WARNING or SYSTEM, and SHALL NOT contain the words "exception", "crash" or "fatal".
11. WHEN any error of this requirement occurs, THE input element SHALL stay enabled (no `disabled` attribute), SHALL keep its value, caret position and selection, and SHALL keep keyboard focus unless criterion 15 applies, and typed lines SHALL be submitted, queued and answered exactly as before, with no change to the game state, the queue or the history caused by the error.
12. WHEN an error occurs, THE Voice_Layer SHALL write exactly one console entry per Voice_Session that contains the Voice_Error_Code and no Spoken_Text, no Cleaned_Text and no raw provider error string.
13. THE Voice_Layer SHALL keep one failure counter for the page lifetime (not reset by a new game), increase it by 1 WHEN a Voice_Session ends with the error code `network` or `other`, reset it to 0 WHEN a final result is processed or a Voice_Session ends with the error code `no-speech`, and leave it unchanged WHEN a Voice_Session ends with the error code `aborted` or a `start` call throws (Requirement 7.17).
14. WHEN several error or end events arrive for one Voice_Session, THE Voice_Layer SHALL apply the outcome of at most one error code per Voice_Session (the first one), and IF an error arrives after a final result of that Voice_Session was processed, or after the Voice_Session was aborted, or while Voice_Availability is `Suspended`, THEN THE Voice_Layer SHALL discard it without a message, a count change or a console entry.
15. WHEN the Mic_Button becomes hidden under this requirement while it has keyboard focus, THE Voice_Layer SHALL move focus to the input element without changing the input's value, caret position or selection.
16. WHEN a Voice_Session ends with an error code, THE Voice_Layer SHALL replace the current Voice_Status text (including `LISTENING...` or a `HEARD: ` preview) with the message of that code, or clear it for `aborted`, within 100 ms of the end event, SHALL announce the same message once in the Voice_Live_Region (nothing for `aborted`), and SHALL clear the message STATUS_CLEAR_MS after it was shown, also when the Mic_Button is hidden by it, unless a newer Voice_Status text replaced it earlier.
17. IF the Speech_Provider `start` call throws, whether on the first activation of the page lifetime or later, THEN THE Voice_Layer SHALL submit no line, set Voice_Availability to `Unavailable` for the rest of the page lifetime, hide the Mic_Button and the Voice_Disclosure, show `VOICE IS NOT AVAILABLE. KEEP TYPING.` in the Voice_Status and announce it once in the Voice_Live_Region, write one console entry with the Voice_Error_Code `other`, and leave the failure counter of criterion 13 unchanged.

### Requirement 8: Transcript cleaning and the shared submission path

**User Story:** As a player, I want what I say to behave exactly like what I type, so that the AI help, the queue and the history work the same.

#### Acceptance Criteria

1. WHEN a final result arrives, THE Voice_Layer SHALL clean each Alternative (at most MAX_ALTERNATIVES) in this order: apply `normalizePlayerText`; map the characters U+2018, U+2019 and U+02BC to an apostrophe (`'`) and U+2010 to a hyphen (`-`); convert to lower case; replace every character other than `a` to `z`, `0` to `9`, apostrophe, hyphen and space by one space; collapse runs of spaces to one space; trim; cut to SPOKEN_TEXT_MAX_CHARS characters and trim again. The same function SHALL be used for the interim text of Requirement 6.3.
2. FOR ALL strings, including empty, very long (at least 10,000 characters), and non-ASCII strings, THE cleaning function SHALL NOT throw, SHALL return a string of at most SPOKEN_TEXT_MAX_CHARS characters that contains only `a` to `z`, `0` to `9`, apostrophe, hyphen and single spaces and has no leading or trailing space, and SHALL be idempotent: cleaning the Cleaned_Text SHALL return the same string (idempotence property).
3. IF the first Alternative is missing, OR the Cleaned_Text of the first Alternative is empty, OR it contains no character from `a` to `z` or `0` to `9`, THEN THE Voice_Layer SHALL submit no line, SHALL show `DIDN'T CATCH THAT.` in the Voice_Status (cleared after STATUS_CLEAR_MS under Requirement 6.5), SHALL announce the same text once in the Voice_Live_Region instead of `Heard: `, SHALL keep Voice_Availability `Ready`, and SHALL count the result as a processed final result for Requirement 7.7.
4. WHEN the Cleaned_Text of the first Alternative is not empty and no Magic_Match, yes/no mapping, Meta_Command block, filename block or phase block of Requirements 9 to 11 and of criterion 12 applies, THE Voice_Layer SHALL submit the Cleaned_Text of the first Alternative, unchanged and in lower case, to the GameController as exactly one line with Input_Origin `spoken`. The Voice_Layer SHALL NOT submit any other Alternative except through a Magic_Match.
5. WHEN a spoken line is submitted, THE GameController SHALL queue, echo, record in history, resolve and deliver it by the same `submit` operation, code path and rules as a typed line of identical text, including the FIFO queue of ai-parser Requirement 3 and the input echo of crt-terminal-ui. The only permitted difference SHALL be the Input_Origin value carried with the line (Requirement 13.1), and a test SHALL show identical transcript, history and engine output for a typed and a spoken line of the same text in the same state with the same seed.
6. WHEN a spoken line is a Classic_Command (decided by the injected predicate `isClassicCommand(text)` supplied to the Voice_Layer through the voice port, which is bound to the running game and wraps `isClassicCommandText` of `src/shared`; the Voice_Layer does not read engine state), THE AI_Parser SHALL make zero network requests for it, exactly as for typed text.
7. WHEN a spoken line is not a Classic_Command and the AI_Parser applies under ai-parser Requirement 2, THE GameController SHALL show the Translation_Line, apply the fallback rules and the Offline_Notice rules of ai-parser Requirement 5, exactly as for a typed line.
8. WHILE the AI_Parser is not installed, THE GameController SHALL give the Cleaned_Text of a spoken line to the classic parser and SHALL show no extra message.
9. WHEN a spoken line is submitted while earlier lines are queued or being resolved, THE GameController SHALL process it in submission order after them, whether those earlier lines are typed or spoken.
10. THE Voice_Layer SHALL read the prompt kind and phase, clean the Alternatives, and make all `submit` calls for one final result (one call, or up to four for a Magic_Match) synchronously within the single invocation of `onFinal`, with no `await`, timer or promise continuation in between, so that two spoken lines can never reorder and no typed line can be interleaved between the lines of one Magic_Match.
11. THE Voice_Layer SHALL NOT call `GameController.submit` for any Spoken_Text while the running game's Game_Mode is Mode_1976, evaluated when the final result arrives.
12. WHEN a final result arrives, THE Voice_Layer SHALL apply these checks in this order and stop at the first that applies: (a) prompt kind or phase cannot be determined, or the phase is not `ready`: submit no line and show no message (Requirement 9.9); (b) prompt kind is `filename`: Requirement 9.5; (c) the Cleaned_Text is empty: criterion 3 of this requirement; (d) prompt kind is `yesno`: the yes/no mapping of Requirement 9.1 and 9.2, else the Meta_Command block of Requirement 9.6, else submission of the Cleaned_Text unchanged (Requirement 9.3); (e) prompt kind is `command`: the Magic_Match of Requirements 10 and 11; (f) the Meta_Command block of Requirement 9.6; (g) criterion 4 of this requirement. Magic words SHALL NOT be recognised at `yesno` or `filename` prompts.
13. WHEN a final result is processed, THE input element SHALL keep the draft text, caret position, selection and keyboard focus that it had before, and a spoken line SHALL NOT clear or overwrite the draft, SHALL NOT change the typed-input history cursor position, and SHALL appear in the history in the same way as a typed line.

### Requirement 9: Prompt kinds, session commands and phases

**User Story:** As a player, I want to answer yes/no questions by voice, and I want dangerous or technical commands to need the keyboard, so that a misheard word cannot quit my game or write files.

#### Acceptance Criteria

1. WHILE the engine prompt kind is `yesno`, WHEN the Cleaned_Text of the first Alternative equals one of `yes`, `yeah`, `yep`, `yup`, `sure`, `ok`, `okay` or `affirmative` (whole-string, case-insensitive comparison on the Cleaned_Text, so `yes please` does not equal `yes`), THE Voice_Layer SHALL submit exactly one line `YES` with Input_Origin `spoken`, and SHALL show `HEARD: ` followed by the Cleaned_Text in the Voice_Status.
2. WHILE the engine prompt kind is `yesno`, WHEN the Cleaned_Text of the first Alternative equals one of `no`, `nope`, `nah` or `negative` (same comparison as criterion 1), THE Voice_Layer SHALL submit exactly one line `NO` with Input_Origin `spoken`, and SHALL show `HEARD: ` followed by the Cleaned_Text in the Voice_Status.
3. WHILE the engine prompt kind is `yesno`, WHEN the Cleaned_Text of the first Alternative is not empty, matches neither list and neither of its first two tokens is a Meta_Command word (criterion 6), THE Voice_Layer SHALL submit the Cleaned_Text unchanged as exactly one line with Input_Origin `spoken`, so that the engine asks its own question again. The Voice_Layer SHALL use only the first Alternative for the yes/no mapping, never the other Alternatives.
4. WHILE the engine prompt kind is `yesno`, THE AI_Parser SHALL send zero requests to the Parse_Endpoint for any spoken or typed line, and THE Voice_Layer SHALL NOT call the matcher of Requirement 10.
5. WHEN a final result is processed and the engine prompt kind read at that moment (criterion 10) is `filename`, THE Voice_Layer SHALL submit no line (nothing is queued, echoed or added to the input history) and SHALL show `TYPE THE FILE NAME.` in the Voice_Status. This covers a prompt that changed to `filename` after the Voice_Session started, because Requirement 4.14 prevents starting a Voice_Session while the prompt kind is `filename`.
6. WHEN the engine prompt kind is `command` or `yesno` AND at least one of the first two tokens (the space-separated words that the classic parser would read) of the Cleaned_Text of the first Alternative makes `isMetaWord` true, THE Voice_Layer SHALL submit no line and SHALL show `TYPE THAT COMMAND; DO NOT SAY IT.` in the Voice_Status.
7. THE Voice_Layer SHALL decide the Meta_Command block with the shared `isMetaWord` function of `src/shared` (and, where a Classic_Command decision is needed, the injected predicate `isClassicCommand(text)` of Requirement 8.6), so that no second word list exists.
8. WHEN the engine prompt kind is `command` and neither of the first two tokens of the Cleaned_Text of the first Alternative makes `isMetaWord` true, but a later token does, THE Voice_Layer SHALL pass the Cleaned_Text to the shared submission path of Requirement 8, which rejects Meta_Commands under ai-parser Requirement 8.
9. IF the prompt kind or the game phase cannot be determined when a final result arrives, OR the game phase is not `ready` at that moment, THEN THE Voice_Layer SHALL submit no line and SHALL show no message.
10. WHEN a final result arrives, THE Voice_Layer SHALL read the prompt kind and the phase at that moment, not at the start of the Voice_Session, and SHALL use those two values for every decision in this requirement.
11. WHEN a final result is withheld under criterion 5, 6 or 9, THE Voice_Layer SHALL leave the GameController queue, the transcript, the input history and the draft text of the input element unchanged, SHALL announce the Voice_Status message of that criterion once in the Voice_Live_Region (criterion 9 announces nothing), SHALL count the result as a processed final result for Requirement 7.7, and SHALL return Voice_Availability to `Ready` within 100 ms (Requirement 5.7).
12. WHEN a final result arrives, THE Voice_Layer SHALL apply the checks in the order of Requirement 8.12 and stop at the first that applies: (a) prompt kind or phase cannot be determined, or the phase is not `ready` (criterion 9); (b) prompt kind is `filename` (criterion 5); (c) the Cleaned_Text is empty (Requirement 8.3); (d) prompt kind is `yesno` (criteria 1 to 3, with the Meta_Command block of criterion 6 before the unchanged submission); (e) prompt kind is `command` (the matcher of Requirements 10 and 11); (f) the Meta_Command block (criterion 6); (g) the submission of Requirement 8.4.

### Requirement 10: Magic-word fuzzy matching

**User Story:** As a player who says "zizzy" or "plover's", I want the game to understand the magic word, so that the speech engine's mistakes do not block the classic moments.

#### Acceptance Criteria

1. THE matcher SHALL be a pure function `matchMagicWords(alternatives)` in `src/voice` that takes an array of Spoken_Text strings in provider order, applies the cleaning of Requirement 8.1 to each string it reads, returns a Magic_Match or no match, uses no clock, no randomness and no I/O, and returns the same result for the same input. An empty array SHALL give no match.
2. FOR ALL inputs, including arrays with 0 to 10 elements and strings that are empty, 10,000 characters long, or non-ASCII, THE matcher SHALL return a result and SHALL NOT throw (totality property).
3. THE Magic_Alias_Table SHALL contain at least these aliases: for XYZZY `xyzzy`, `zizzy`, `sizzy`, `x y z z y`; for PLUGH `plugh`, `plug`, `plu`, `plug h`; for PLOVER `plover`, `plovers`, `plover's`, `plove`; for FEE `fee`; for FIE `fie`, `fi`; for FOE `foe`, `fo`; for FOO `foo`, `fum`; and at least four aliases for each of XYZZY, PLUGH and PLOVER.
4. WHEN a token run (after the tokenization of criterion 18) equals an alias exactly, THE matcher SHALL return a Magic_Match with tier `alias`. A token may first lose a trailing `'s` or `s` only if the remaining token is itself an alias of five or more letters (so `plovers`, `plover's` and `xyzzys` match, while `plugs`, `fee's` and `lovers` do not).
5. WHEN a single token has five or more letters, is not in the Stop_List, and has a Damerau-Levenshtein distance of 1 to the canonical word XYZZY, PLUGH or PLOVER (insertion, deletion, substitution, or swap of two adjacent letters), THE matcher SHALL return a Magic_Match with tier `edit`. A token at distance 0 is handled by criterion 4. The edit tier SHALL be tried only after the alias tier has failed for the whole utterance.
6. THE matcher SHALL apply neither the edit-distance tier nor any other fuzzy rule to tokens of four or fewer letters, to tokens that are part of a run of two or more tokens, or to the canonical words FEE, FIE, FOE and FOO; such tokens SHALL match only by exact alias.
7. IF the tokens of an utterance are not, after one optional lead-in from the list `say the magic word`, `say the word`, `the word`, `magic word`, `say` (tried longest first, at most one lead-in), exactly one Magic_Word run, THEN THE matcher SHALL return no match. A lead-in alone, a lead-in followed by any other token, and any token before the lead-in SHALL give no match.
8. WHEN a final result has several Alternatives, THE matcher SHALL examine at most the first MAGIC_ALTERNATIVES_CHECKED Alternatives in provider order and return the Magic_Match of the first one that matches, with the index (0-based) of that Alternative, IF the Cleaned_Text of the first Alternative, after removal of the lead-in and after the joining of criterion 18, has at most MAGIC_TOP_TOKEN_LIMIT tokens; otherwise it SHALL return no match. A Magic_Match SHALL win over a Classic_Command reading of the same Alternative.
9. WHEN the matcher returns a Magic_Match and the prompt kind is `command` (criterion 16), THE Voice_Layer SHALL submit each canonical command of it as its own line with Input_Origin `spoken`, in order and in the same task (Requirement 8.10), echoed as the canonical upper-case command.
10. WHEN the Voice_Layer submits the lines of a Magic_Match, THE Voice_Layer SHALL show `HEARD: ` followed by the Cleaned_Text of the matching Alternative (cut to PREVIEW_MAX_CHARS characters) in the Voice_Status, and SHALL make exactly one `Heard: ` announcement of that text in the Voice_Live_Region for the processed final result.
11. THE Magic_Alias_Table SHALL contain no alias that is a Game_Vocabulary word, except the spellings of the Magic_Words themselves (`xyzzy`, `plugh`, `plove`, `plover`, `fee`, `fie`, `foe`, `foo`, `fum`).
12. FOR ALL aliases in the Magic_Alias_Table and for all variants of an alias with upper case, a trailing period, a leading lead-in of criterion 7, or leading and trailing whitespace, THE matcher SHALL return the Magic_Match of that alias, with the Magic_Match of the alias without the variant as the expected value (alias property).
13. FOR ALL Game_Vocabulary words other than the exceptions in criterion 11, THE matcher SHALL return no match (ordinary-vocabulary property).
14. FOR ALL words in a checked-in corpus of at least 200 ordinary English words that includes `plush`, `plum`, `plus`, `plug in`, `plough`, `flush`, `fizzy`, `dizzy`, `fuzzy`, `clover`, `lover`, `lovers`, `free`, `feet`, `fee's`, `few`, `fly`, `fool`, `food`, `for`, `four`, `fun`, `fur` and every word of the Stop_List, THE matcher SHALL return no match. THE Stop_List SHALL contain at least 30 words, including `plush`, `plugs`, `plough`, `clover`, `lover`, `fizzy`, `dizzy` and `fuzzy`, and SHALL contain every ordinary English word of the corpus that has five or more letters and a Damerau-Levenshtein distance of 1 to XYZZY, PLUGH or PLOVER.
15. THE typed path SHALL NOT call the matcher: the classic parser, the AI_Parser and the GameController SHALL NOT import it (verified by a static import test), and a typed `zizzy` SHALL reach the engine unchanged.
16. WHILE the engine prompt kind is not `command`, THE Voice_Layer SHALL ignore any Magic_Match and SHALL apply Requirement 9 to the Cleaned_Text instead; the prompt kind and phase are read when the final result arrives (Requirement 9.10), and IF either cannot be determined, THEN no line SHALL be submitted (Requirement 9.9).
17. IF the matcher returns no match, THEN THE Voice_Layer SHALL continue with the rules of Requirements 8 and 9 for the first Alternative, unchanged and without the Magic_Match handling of criteria 9 and 10. In particular `xyzzy xyzzy`, `xyzzy plugh`, `go xyzzy` and `zizzy please` SHALL give no match.
18. THE matcher SHALL tokenize a Cleaned_Text by splitting on spaces and hyphens, and SHALL join every run of two or more consecutive single-letter tokens into one token before matching and before counting tokens, so that `x y z z y` counts as one token `xyzzy` and `fee-fi-fo-fum` counts as four tokens `fee`, `fi`, `fo`, `fum`.

### Requirement 11: The FEE FIE FOE FOO sequence

**User Story:** As a player, I want to say "fee fie foe foo" in one breath, so that the eggs spell works by voice the way it does when typed line by line.

#### Acceptance Criteria

1. WHEN the token run of an utterance (after the optional lead-in of Requirement 10.7) has exactly four tokens that match, in this order, an alias of FEE, an alias of FIE, an alias of FOE and an alias of FOO, THE matcher SHALL return a Magic_Match with tier `alias` and the four commands `FEE`, `FIE`, `FOE`, `FOO` in that order, so that `fee fie foe foo` and `fee fi fo fum` both match. FOR the purpose of this requirement, THE matcher SHALL treat a hyphen between two letters as a token separator, so that `fee-fi-fo-fum` gives the same result as `fee fi fo fum`.
2. WHEN the token run (after the optional lead-in) has two or three tokens and each token matches, in order, the aliases of FEE, FIE and (for three tokens) FOE, THE matcher SHALL return a Magic_Match with tier `alias` and those two or three commands in order. A one-token run is decided by Requirement 10 alone.
3. IF the token run has two or more tokens and any of the following is true, THEN THE matcher SHALL return no match for the utterance: the first token is not an alias of FEE; two neighbouring tokens are aliases of the same Magic_Word (for example `fee fee fie` or `fi fie`); a word is skipped (for example `fee foe`); the order differs from FEE, FIE, FOE, FOO; the run has more than four tokens (for example `fee fie foe foo foo` or the whole sequence said twice); or any token is not an alias of a Magic_Word of the Magic_Sequence (for example `fee fie plugh`).
4. WHEN a Magic_Match has several commands, THE Voice_Layer SHALL submit them as separate spoken lines, each with Input_Origin `spoken`, in order, within the same task as the final event (Requirement 8.10) and after any lines that are already queued, and THE GameController SHALL echo and deliver each line as its own line, so that the engine's own sequence logic decides the result. THE Voice_Layer SHALL submit all lines of the Magic_Match even if an earlier line changes the engine state (for example a death), and THE matcher SHALL keep no memory between utterances, so that `fee` said now and `fie foe foo` said later behave as the engine decides.
5. THE Voice_Layer SHALL NOT call the AI_Parser, SHALL make zero network requests, and SHALL show no Translation_Line for any line of a Magic_Match.
6. FOR ALL runs formed by concatenating the aliases of the Magic_Sequence in order (all four, and each prefix of two or three), the matcher SHALL return the corresponding commands in order, and FOR ALL runs of two or more tokens that are aliases of Magic_Words and are neither the Magic_Sequence nor a prefix of it of two or three words (any other order, repeat, skip or length), the matcher SHALL return no match (sequence property).
7. WHILE the engine prompt kind is not `command`, THE Voice_Layer SHALL NOT split a run into a Magic_Match, and SHALL handle the Cleaned_Text under Requirement 9 (yes/no mapping or filename block) instead.
8. FOR a run under criteria 1 and 2, THE token limit MAGIC_TOP_TOKEN_LIMIT of Requirement 10.8 SHALL count only the tokens after the lead-in, so that `say the magic word fee fie foe foo` is examined like `fee fie foe foo`.
9. WHEN a Magic_Match of several commands is returned, THE Voice_Layer SHALL show `HEARD: ` followed by the Cleaned_Text of the matching Alternative once in the Voice_Status and SHALL make exactly one `Heard: ` announcement of it in the Voice_Live_Region for the processed final result (not once per command), and THE matcher SHALL pick the first Alternative, in provider order among the first MAGIC_ALTERNATIVES_CHECKED, that gives any Magic_Match, even if a later Alternative would give a longer sequence.

### Requirement 12: The spoken-word rule for XYZZY

**User Story:** As a player of Haunted mode, I want XYZZY to need my voice, so that the magic word feels magic, and I want to be able to finish the game even if I cannot or do not want to talk.

#### Acceptance Criteria

1. WHILE the Game_Mode is Haunted_Mode, the engine prompt kind is `command`, Voice_Availability is `Ready` or `Busy`, and the Deflection_Count of the current game is less than DEFLECTION_LIMIT, WHEN a line of Input_Origin `typed` reaches delivery and the final engine-bound text that the GameController would give to `step` contains the XYZZY motion word, THE Input_Gate SHALL deflect the line. The conditions SHALL be evaluated at the moment the Input_Gate runs for that line (delivery), not when the line was submitted.
2. THE Input_Gate SHALL decide "contains the XYZZY motion word" with the engine's own vocabulary lookup on the final engine-bound text (after any AI translation and after input transformers). A word counts when the lookup resolves it to the XYZZY motion, so matching is case-insensitive and uses the classic parser's first-5-characters rule, in either of the at most two words of the line. `xyzzy`, `XYZZY`, `go xyzzy`, `say xyzzy`, `plugh xyzzy` and a typed sentence that the AI_Parser translates to a command containing XYZZY SHALL all be deflected, and the whole line is withheld from `step`. Whether XYZZY would have an effect in the current room SHALL NOT influence the decision.
3. WHEN the Input_Gate deflects a line, THE GameController SHALL NOT call `step`, SHALL keep the typed line in the transcript echo and the input history, SHALL show exactly one Narrator_Line (the Deflection_Line) and no Original_Text (a Translation_Line for an AI-translated line MAY precede it), and SHALL increase the Deflection_Count by 1. The `serialize` output of the engine state SHALL be byte-identical before and after the deflected line, so that no game turn, no engine output, no lamp or dwarf movement and no random number is consumed.
4. THE Deflection_Line SHALL be the one fixed string `SAY IT ALOUD. HOLD THE MIC OR ALT+M. TYPE XYZZY AGAIN IF YOU MUST.` (66 characters), identical on every Deflection, with no randomly chosen part. It contains the upper-case character sequences `ALOUD`, `MIC` and `ALT+M`, and the upper-case style matches the other fixed one-line texts of this spec.
5. WHILE the Deflection_Count of a game equals DEFLECTION_LIMIT, THE Input_Gate SHALL let every typed line that contains XYZZY reach `step` unchanged, so that the next typed XYZZY after the Deflection, and every later one in that game, works normally. Typed lines without XYZZY between the Deflection and the next typed XYZZY SHALL NOT affect this.
6. WHEN a new game starts (from the boot, from the restart offer after a game has ended, from a mode change that starts a game, or after an invalid or cleared autosave), THE GameController SHALL set the Deflection_Count to 0; WHEN a valid autosaved game is restored, THE GameController SHALL set the Deflection_Count to the value decoded under Requirement 13.11. A death and reincarnation within a game is the same game and SHALL NOT reset the Deflection_Count.
7. WHEN a line of Input_Origin `spoken` contains the XYZZY motion word, THE Input_Gate SHALL let it reach `step` unchanged, whether it came from the Magic_Match of Requirement 10, from an exact spoken classic command or from the AI_Parser, and the Deflection_Count SHALL stay unchanged.
8. WHILE Voice_Availability is `Unsupported`, `Unavailable` or `Suspended`, OR the Game_Mode is Mode_1976, OR no Voice_Layer is installed (including while the Voice_Layer chunk is still loading), THE Input_Gate SHALL let every typed XYZZY reach `step` unchanged and SHALL NOT change the Deflection_Count.
9. WHEN Voice_Availability changes to `Unavailable` during a game, THE Input_Gate SHALL stop deflecting from that moment, including for lines already queued at that moment, and the Deflection_Count SHALL be retained.
10. THE Input_Gate SHALL NOT deflect the words PLUGH, PLOVER, FEE, FIE, FOE or FOO, and SHALL NOT deflect any prompt kind other than `command` (a typed `xyzzy` answering a `yesno` or `filename` prompt SHALL reach `step` unchanged and SHALL NOT change the Deflection_Count).
11. THE Input_Gate SHALL NOT change the text given to `step` for a line that it lets through, so that Original_Text for a spoken XYZZY is byte-identical to Original_Text for a typed XYZZY in the same state with the same seed.
12. THE README SHALL document the rule, the shortcut (Alt+M), the once-per-game hint, the fact that the next typed XYZZY works normally, and the fact that the game is completable without a microphone.
13. WHILE the Game_Mode is Haunted_Mode, in every Voice_Availability, THE game SHALL be completable to 430 points with typed input only, including every use of XYZZY, and a walkthrough test that types XYZZY with a stub Voice_Layer in `Ready` SHALL reach 430 points when it types the deflected XYZZY a second time.
14. WHEN a Deflection occurs, THE GameController SHALL increase the Deflection_Count and then write the autosave immediately afterwards (including when no `step` has run), so that the Deflection_Count survives a page reload and the same game is never deflected twice.
15. IF the autosave write after a Deflection fails, THEN THE GameController SHALL still show the Deflection_Line, SHALL keep the increased Deflection_Count in memory for the rest of the page lifetime, SHALL show no error to the player, and SHALL let the next typed XYZZY reach `step`.
16. THE Deflection_Count SHALL NOT be changed by an engine `SAVE` or `RESUME` command, by a death and reincarnation within the same game, or by any line of Input_Origin `spoken`.
17. WHEN several typed lines that contain XYZZY are queued while the Deflection_Count is 0, THE GameController SHALL process them in FIFO order and evaluate the Input_Gate for each at its own delivery, so that the first is deflected and the second and later ones reach `step`.

### Requirement 13: Controller and hook seams

**User Story:** As a developer, I want the smallest possible changes to the terminal UI, so that the existing typed behaviour and tests stay exactly as they are.

#### Acceptance Criteria

1. THE GameController `submit` operation SHALL accept an optional Input_Origin parameter whose default is `typed`, SHALL keep the origin with each queued line until that line is delivered (queued lines of both origins are delivered in submission order), and SHALL treat any value other than `spoken` as `typed`.
2. THE `ResolveContext` type SHALL carry the Input_Origin of the line being resolved as an optional field, and THE GameController SHALL set it for every call to `needsTranslation` and `translate`, so that the AI_Parser path ignores it and a later spec can use it; the outcome of the AI_Parser for the same text, state and context SHALL be identical for `typed` and `spoken`.
3. THE ExtensionHooks registry SHALL provide `addInputGate(fn)` returning a disposer. A gate SHALL receive (a) the exact string that would be given to `step`, which is the text after AI resolution and after `transformInput`, (b) the Input_Origin, (c) the Deflection_Count as a plain number, and (d) a frozen HookContext (which carries the prompt kind). A gate SHALL return synchronously either an allow result or a deflect result carrying an array of 1 to 3 non-empty Narrator_Line strings. THE disposer SHALL remove the gate, SHALL be safe to call more than once, and a gate added or removed while a line is being evaluated SHALL NOT affect that evaluation.
4. WHEN the Game_Mode is `haunted`, THE ExtensionHooks registry SHALL call the gates in registration order and SHALL stop at the first deflect result (later gates are not called for that line); WHILE the Game_Mode is not `haunted`, THE registry SHALL call no gate and SHALL return allow. IF a gate throws, returns a Promise, returns a value that is neither an allow nor a valid deflect result (including a deflect with zero lines, a non-array, or a non-string or empty entry), THEN THE registry SHALL treat that gate as allow, SHALL log the error through the Logger, and SHALL continue with the next gate, in the same way as `transformInput`.
5. THE GameController SHALL evaluate the gates inside every call of `deliver`, after AI resolution (including the paths that deliver the raw line because the AI was skipped, failed, timed out or the state changed) and after `transformInput`, and before `step`, so that an AI-translated line is also checked. Lines handled before `deliver` (the `NEW`/blank line in the `over` phase) SHALL NOT be gated.
6. THE GameController SHALL expose read-only `promptKind`, `phase` and `gameMode` getters (`phase` and `gameMode` already exist; `gameMode` is `undefined` when no game is running), and SHALL keep the existing game-start notification (`onGameStart`), called synchronously once per game start (boot, new game after game over, restore of an autosaved game) with the running game's own Game_Mode, so that the main entry can start and stop the Voice_Layer. IF the notification handler throws, THEN THE GameController SHALL log the error and continue; an in-game engine `SAVE` or `RESUME` SHALL NOT trigger the notification.
7. THE Input_Gate contract and the voice port that the Mic_Button DOM module uses SHALL be types defined in `src/ui` that `src/voice` and `src/haunt` satisfy structurally, in the way that `InputResolver` is satisfied by `src/parser`, so that no file in `src/ui` imports from `src/voice`, `src/haunt` or `src/parser` (checked by the static test of Requirement 18.9).
8. THE composition in `src/main.ts` SHALL fan one game-start notification out to the AI loader and to the voice loader, each with its own at-most-once and mode rules; IF one loader throws or its import fails, THEN THE other loader SHALL still be called for that notification and the failure SHALL be logged only.
9. WHEN no gate and no Voice_Layer are installed, THE GameController SHALL behave exactly as before this feature, meaning identical transcript, identical autosave bytes and identical engine output for the same inputs and seed, and every test that exists in `tests/` before this feature SHALL pass without an edit to an existing assertion, except the layering rule that Requirement 18.9 changes in `tests/ui-layering.test.ts`.
10. THE changes of this spec SHALL leave every file under `src/engine`, `src/data`, `src/parser`, `original` and `reference` unmodified (an empty diff against the commit before this feature).
11. THE autosave record in `src/ui/autosave.ts` SHALL accept the optional field `ui` of the shape `{ deflections: integer }` and keep `v` equal to `1`; THE encoder SHALL write `ui` only when the Deflection_Count is greater than 0, so that an autosave without a Deflection is byte-identical to one written before this feature; THE decoder SHALL read an absent `ui` field, a non-object `ui`, or a `deflections` that is not an integer from 0 to DEFLECTION_LIMIT (for example a fraction, a negative number, a number above DEFLECTION_LIMIT, NaN or a string) as a Deflection_Count of 0 without rejecting the record or any other field of it, SHALL ignore unknown keys inside `ui`, and SHALL decode every autosave written before this feature exactly as before (backward compatibility); THE `serialize` and `deserialize` functions of the engine and the `GameState` shape SHALL remain unchanged.
12. FOR ALL valid autosave records with a Deflection_Count from 0 to DEFLECTION_LIMIT, encoding then decoding SHALL return the same Deflection_Count and the same values for every other field (round-trip property).
13. WHEN the GameController accepts a deflect result, THE GameController SHALL increase the Deflection_Count by 1 but never above DEFLECTION_LIMIT, so that every value it writes to the autosave is one the decoder accepts.
14. WHEN the GameController accepts a deflect result, THE GameController SHALL show each returned string, in array order, as a line of kind `narrator`, SHALL NOT call `step`, SHALL NOT notify the resolver that the command was accepted, SHALL keep any Translation_Line already shown for that line, and SHALL leave the engine state, the prompt kind, the phase and the input history unchanged apart from the echo of the line.
15. WHENEVER the GameController writes the autosave (after a `step`, after a restore, and after a deflect), THE GameController SHALL pass the current Deflection_Count to the encoder, so that a `step` after a Deflection does not drop the `ui` field.

### Requirement 14: Privacy and disclosure

**User Story:** As a player, I want to see where my voice goes before I use the microphone, and I want to start talking with one press or tap, so that I can choose to type instead and am never slowed down.

#### Acceptance Criteria

1. THE System SHALL NOT call `getUserMedia`, SHALL NOT create a `MediaRecorder`, SHALL NOT create any audio node that takes microphone input (for example from `createMediaStreamSource`; Web Audio used for synthesized sound is not restricted by this spec), and SHALL NOT read, buffer, record or store audio data in application code; the only audio capture SHALL be the browser's own capture inside `SpeechRecognition`, started by the Web_Speech_Adapter.
2. THE System SHALL NOT store Spoken_Text in any place except the input echo line of a submitted spoken line, which is stored exactly like a typed line (transcript, input history and autosave kind `input`), and SHALL NOT store interim text, non-selected Alternatives or the Input_Origin of a line.
3. THE System SHALL NOT send Spoken_Text over the network in application code, except when a submitted spoken sentence that is not a Classic_Command goes to the AI_Parser under the ai-parser privacy statement.
4. WHILE Voice_Availability is `Ready` or `Busy` and the running game's Game_Mode is Haunted_Mode, THE Voice_Disclosure SHALL be visible next to the Mic_Button, meaning: it has no `hidden` attribute, it is a DOM sibling in the same container as the Mic_Button, it has a rendered height greater than 0, it is not clipped or covered, and its text is shown permanently, not only on hover, focus or press. It SHALL consist of one element whose `textContent`, after trimming ASCII whitespace, equals the Voice_Disclosure_Text exactly, with no child markup. THE Voice_Disclosure_Text SHALL be defined once, in a single exported constant (module location chosen by design), and `index.html`, the tests and `scripts/check-dist.ts` SHALL all equal that constant. It SHALL be shown in every Mic_Button state, including the `aria-disabled="true"` state of Requirement 4.14.
5. WHILE Voice_Availability is `Unsupported`, `Unavailable` or `Suspended`, OR the running game's Game_Mode is Mode_1976, THE Voice_Disclosure SHALL carry the `hidden` attribute. THE Voice_Disclosure SHALL change its `hidden` state in the same synchronous DOM update as the Mic_Button, so that it is never visible without the Mic_Button and the Mic_Button is never visible without it.
6. THE Voice_Disclosure SHALL be text in the DOM (not an image, canvas or CSS-generated content), SHALL NOT carry `aria-hidden`, and SHALL NOT be announced in the Voice_Live_Region. WHILE the Voice_Disclosure is visible, THE `aria-describedby` of the Mic_Button SHALL list the id `mic-disclosure` first; WHILE Requirement 4.14 applies, THE `aria-describedby` SHALL additionally reference the element that carries the text "Voice input is not available for this question", listed after `mic-disclosure`.
7. THE Voice_Disclosure SHALL keep a WCAG contrast ratio of at least 4.5:1 against the terminal background under the same worst-case dimming as Requirement 17.5. THE Voice_Disclosure SHALL wrap its complete text onto several lines and SHALL NOT truncate, clip or ellipsize it. At a viewport width of 320 CSS pixels, THE document SHALL have no horizontal scrollbar (`scrollWidth` not greater than `clientWidth`).
8. WHEN the Mic_Button is activated for the first time in the page lifetime (by a mouse or pen `pointerdown`, by a Touch_Click, by Enter or Space, or by Alt+M), THE Voice_Layer SHALL request the Voice_Session start in the event-handler task of that activation (for touch, the task of the `click`, not of the `pointerdown`), and THE browser's own permission prompt SHALL be the only consent step. THE Voice_Layer SHALL show no dialog, no notice, no confirmation and no second-press requirement before that first Voice_Session; the only permitted additional UI is the Voice_Status text of Requirement 6.
9. THE System SHALL NOT read or write any consent record: no KeyValueStore entry, cookie, web storage entry or other persisted flag SHALL record that the Voice_Disclosure was seen, that the Mic_Button was used, or that permission was granted or denied. (The Autosave_Voice_Field `ui.deflections` is not a consent record.)
10. THE README and the credits page SHALL each state, using these exact phrases (case-sensitive, matching Requirement 16.4): "voice input uses the speech recognition service" of the "maker of the browser"; audio is sent to that service for recognition (which company that is depends on the browser); this site "never records or stores audio"; "1976 mode never uses the microphone"; "typing always works". Any test that checks the Voice_Disclosure_Text SHALL import it from the single exported constant of criterion 4.
11. WHILE the Voice_Disclosure is visible, THE Voice_Disclosure SHALL NOT offer a close, collapse, "don't show again" or acknowledge control, and SHALL stay visible before, during and after every Voice_Session, including after the browser has granted permission.
12. IF the browser's permission prompt is denied or dismissed (Voice_Error_Code `denied`), THEN THE Voice_Layer SHALL show no further permission request, no retry prompt and no explanation dialog, SHALL set Voice_Availability to `Unavailable` as defined in Requirement 7 and 2.14, and THE Voice_Disclosure SHALL be hidden together with the Mic_Button under criterion 5; typed input SHALL remain unaffected and the game state SHALL be unchanged.
13. THE static tests SHALL assert that `src/ui`, `src/main.ts` and `src/voice` contain no `getUserMedia`, no `MediaRecorder` and no microphone-input audio node, and that the only identifiers writing to storage in `src/voice` are absent (no storage, cookie or KeyValueStore call).

### Requirement 15: Content-Security-Policy and Permissions-Policy

**User Story:** As the project owner, I want the headers to allow the microphone for this site only and nothing else, so that the feature works and the policy stays tight.

#### Acceptance Criteria

1. THE file `public/_headers` SHALL contain exactly one header line `Permissions-Policy: microphone=(self)` (unquoted `self` token, no other directives on that line), indented under the single path-pattern block `/*`, so that the header is set on every static response.
2. THE `microphone` allowlist in `public/_headers` SHALL consist of exactly `(self)`: THE file SHALL NOT contain `microphone=()`, `microphone=*`, `microphone=(*)`, `microphone=(self "<origin>")` or any quoted origin in any `microphone` allowlist.
3. THE Content-Security-Policy line in `public/_headers` SHALL keep the directives `default-src 'self'` and `connect-src 'self'`, SHALL contain no source that starts with `http:`, `https:`, `ws:`, `wss:` or `*`, SHALL contain no `'unsafe-inline'` or `'unsafe-eval'` token, and SHALL NOT gain a `media-src`, `script-src` or `connect-src` source other than `'self'` (and `data:` only where `img-src` has it today) for the sake of speech recognition.
4. THE Content-Security-Policy SHALL keep `frame-ancestors 'none'`, so that no other page can embed the game and request the microphone for it.
5. THE `public/_headers` file SHALL keep the lines `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` byte-for-byte unchanged, and SHALL keep the existing Content-Security-Policy directives `img-src 'self' data:`, `style-src 'self'` and `font-src 'self'`.
6. THE README SHALL state that `_headers` applies to static assets only (not to responses of the Functions under `/api`), that the microphone policy is set there, that the Vite development server does not apply `_headers` (so header problems only show on the deployed site or a Pages preview), and that the CSP needs no new origin for speech recognition because the browser, not page script, contacts the speech service.
7. IF the manual check on the deployed site finds that Content-Security-Policy or Permissions-Policy blocks recognition in Chrome, Edge or Safari (symptom: the first press ends with a `denied` or `network` Voice_Error_Code although the browser permission prompt was accepted), THEN THE project owner SHALL record the browser, version and symptom in the README, and THE headers SHALL be changed together with their tests in a follow-up to this spec; THE headers of this spec SHALL ship unchanged until then.
8. THE tests for this requirement SHALL parse `public/_headers` (not just search for substrings) and assert criteria 1 to 5 against the parsed result: exactly one `/*` block, exactly one `Permissions-Policy` line, exactly one Content-Security-Policy line, and the directive-level conditions above. THE tests SHALL run in `vitest --run` without a browser.
9. WHERE `public/_headers` contains a second path-pattern block besides `/*`, THE tests of criterion 8 SHALL fail unless that block repeats no `Permissions-Policy`, `Content-Security-Policy` or `X-Content-Type-Options` header with a different value, because Cloudflare Pages merges the headers of all matching blocks.
10. THE README SHALL list, as "not verified before release", that (a) whether `Permissions-Policy: microphone` also governs `SpeechRecognition.start()` in each browser, and (b) whether Content-Security-Policy `connect-src` affects the browser's own connection to the speech service, are verified only by the manual checklist of Requirement 16.8 and not by any automated test.

### Requirement 16: Documentation and build checks

**User Story:** As a maintainer, I want the build to fail when the voice documentation, the headers or the lazy loading are wrong, so that a regression cannot ship.

### Requirement 19: Scope boundaries

**User Story:** As the owner of the spec set, I want clear edges between this spec and the next ones, so that nothing is built twice and nothing is left out.

#### Acceptance Criteria

1. THE System SHALL NOT call `speechSynthesis` or `speechSynthesis.speak`, and SHALL NOT construct a `SpeechSynthesisUtterance`, in any file added or changed by this spec; speech output belongs to the later voice-output spec.
2. THE Voice_Layer SHALL expose a read-only boolean `listening` state and a `subscribe(listener)` operation that returns a disposer, so that the voice-output spec can cancel speech while a Voice_Session is running. `listening` SHALL be true from the moment a Voice_Session starts until it ends or is aborted, and false otherwise.
3. WHEN `listening` changes value, THE Voice_Layer SHALL call every subscribed listener once, synchronously, with the new value. THE Voice_Layer SHALL NOT call a listener when the value is unchanged. A disposed listener SHALL NOT be called again. A listener that throws SHALL NOT stop the other listeners from being called and SHALL NOT change `listening`.
4. THE System SHALL NOT add a hosted speech-to-text provider, a Worker endpoint, a Worker secret, a Worker binding or a `fetch` call to an origin other than the page's own in this spec; the Speech_Provider interface is the only preparation for it.
5. THE System SHALL NOT add narrator content beyond the Deflection_Line of Requirement 12.4: no other Narrator_Line, no narrator line for a Voice_Error_Code, and no narrator line for a Magic_Match, a failed recognition or a denied permission. Voice_Status, Voice_Live_Region and Voice_Disclosure messages are not Narrator_Lines and SHALL NOT be written to the transcript. The narrator spec owns all other Narrator_Lines.
6. THE System SHALL NOT add a persisted voice setting or consent record. The only new persisted value SHALL be the Deflection_Count in the Autosave_Voice_Field, which is per-game state and not a setting. No voice code SHALL write to `localStorage`, `sessionStorage`, `IndexedDB` or cookies, and no audio, Spoken_Text, Voice_Status text or Voice_Availability value SHALL be persisted by any path other than the existing input echo and history that a submitted spoken line shares with a typed line (Requirement 14.2).
7. THE typed classic parser, the engine's vocabulary matching and the engine's output SHALL remain exactly as they are: the cleaning of Requirement 8 and the magic-word matcher SHALL act only before `step` and only on lines of Input_Origin `spoken`, and the Input_Gate SHALL act only before `step` and only while the Game_Mode is Haunted_Mode. The only changes to existing modules SHALL be the seams listed in Requirement 13 (`submit` origin parameter, `ResolveContext` field, `addInputGate`, read-only getters, game-start subscription, optional autosave `ui` field).
8. THE changes of this spec SHALL leave `src/engine`, `src/data`, `src/parser`, `original` and `reference` unmodified, and the replay of every upstream `.log` against its `.chk` SHALL still pass without an edit to a test.
9. THE System SHALL NOT add a text-to-speech feature, a Worker or AI-parser change, a haunting effect, or an in-game voice settings screen in this spec; the later voice-output, narrator and haunt specs own them.

## Open Questions and Decisions

### Decided

- **OQ-1: How strictly "XYZZY must be spoken aloud" applies. Decided:** the narrator deflects a typed XYZZY once per game (DEFLECTION_LIMIT = 1), even where XYZZY would do nothing in the current room; the next typed XYZZY works, and typed XYZZY always works while voice is unusable; the Deflection never calls `step`, a death and reincarnation does not reset the count, and the count survives a reload through the Autosave_Voice_Field [Requirements 12, 13.11, 17.8].
- **OQ-2: Where the Deflection_Line comes from. Decided:** one fixed Narrator_Line owned by this spec (`SAY IT ALOUD. HOLD THE MIC OR ALT+M. TYPE XYZZY AGAIN IF YOU MUST.`), with no Original_Text, no turn and no random number [Requirements 12.3, 12.4, 19.5].
- **OQ-3: Push-to-talk keyboard shortcut. Decided:** Alt+M follows the same rule as the pointer (hold for 250 ms or more is push-to-talk, a shorter tap latches), plus the focused button toggling on Enter or Space [Requirements 4.6, 4.7, 4.8, 4.11, 17.2].
- **OQ-4: Tap behaviour. Decided:** a mouse or pen press shorter than MIN_HOLD_MS (250 ms) latches listening, a longer press is hold-to-talk; on touch there is no hold: a tap toggles Latch_Mode on the `click` (see OQ-13) [Requirements 4.2, 4.3, 4.17, 4.18].
- **OQ-5: Consent UX. Decided:** no consent flow; an always-visible Voice_Disclosure next to the Mic_Button, the first press starts listening, and the browser's own permission prompt is the consent moment; no consent record is stored [Requirements 4.1, 14.4 to 14.9].
- **OQ-6: Meta_Commands by voice. Decided:** spoken QUIT, SAVE, RESUME, SEED and WASTE are not submitted; the player types them [Requirements 9.6, 9.8].
- **OQ-7: Echo of fuzzy-matched magic words. Decided:** the transcript echoes the canonical command, and the heard text goes to the Voice_Status and the Voice_Live_Region [Requirement 10.9, 10.10].
- **OQ-8: Yes/no and file-name prompts by voice. Decided:** spoken answers to `yesno` prompts are supported with whole-utterance alias matching; `filename` prompts are not, and the player types the name [Requirements 9.1 to 9.5].
- **OQ-9: Fuzzy matching rules. Decided:** alias tier plus edit distance 1 for tokens of five or more letters, a Stop_List, no fuzzy rule for short tokens, and the positional meaning of "fum" only inside a multi-token run (a single `fum` also matches by exact alias, see the defaults below) [Requirements 10, 11].
- **OQ-10: How long a hidden microphone button stays hidden. Decided:** after a runtime error (Requirement 7.1, 7.2, 7.7, 7.17) or a failed start (Requirement 2.14) for the rest of the page lifetime, not stored, so a reload retries; after a permission-based `denied` found at detection, until the permission changes to granted or prompt [Requirements 2.5, 7.8].
- **OQ-11: Contextual biasing with `phrases`. Decided:** use it where the browser supports it, ignoring any failure [Requirement 3.7].
- **OQ-12: Wording of the Voice_Disclosure_Text and the Deflection_Line. Decided:** the Voice_Disclosure_Text is fixed in the glossary and says "stores no audio" rather than "stores nothing", because a submitted spoken line is stored as an input echo like a typed line (Requirement 14.2); the Deflection_Line is fixed in Requirement 12.4. The owner may still polish the jokes in a later pass; any change must keep the tested phrases.
- **OQ-13: Touch activation. Decided:** on touch input, recognition starts on the `click` that follows the touch press (a guaranteed user activation), not on `pointerdown`. Hold-to-talk applies to mouse and pen only; a touch tap toggles Latch_Mode (first Touch_Click starts, next calls `stop`) with no MIN_HOLD_MS decision; Alt+M keeps its hold and tap-latch behaviour; a touch press still does not dismiss the on-screen keyboard and one tap never starts and stops twice. The Mic_Button uses `touch-action: manipulation` so that the click is delivered reliably and a double tap does not zoom, and still suppresses the context menu of a long press [Requirements 4.1 to 4.5, 4.9, 4.12 to 4.19, 14.8, 16.8(g), 18.4, 18.12].
- **OQ-14: A failed start hides the button. Decided:** the Mic_Button is shown wherever `SpeechRecognition` or `webkitSpeechRecognition` exists (a Firefox build that ships the API included; no browser is special-cased). If `start()` fails with `not-allowed`, `service-not-allowed` or an unsupported condition (`language-not-supported`, or `start` throwing, including synchronously on the first activation), Voice_Availability becomes `Unavailable` for the rest of the page lifetime, the Mic_Button and the Voice_Disclosure are hidden, only the calm status line is shown, and typing keeps working. The behaviour for `network`, `other` and `no-speech` errors is unchanged (stay `Ready`; hide after REPEATED_ERRORS_BEFORE_HIDE) [Requirements 2.13, 2.14, 5.8, 7.1, 7.2, 7.8, 7.13, 7.17, 16.8(d)].

### Defaults from the detailing pass, now Decided

These user-visible defaults were chosen when the requirements were refined and have all been approved by the project owner (status: Decided). The requirements above follow them; a later change would alter the requirements named in brackets.

- **D-1: Alt+M tap latches. Decided (approved).** A short Alt+M tap (under 250 ms) keeps listening until the next Alt+M, Enter or Space on the button, a result, or 10 seconds, exactly like a short pointer tap [Requirements 4.7, 4.8, 17.2].
- **D-2: A denied permission at page load is recoverable; a runtime error is not. Decided (approved).** If the browser already reports the microphone as `denied` at start-up, the button stays hidden but comes back if the player later allows the microphone in the browser settings; after a `denied` or other fatal error during a session, a `start` that throws, or three failed sessions in a row, the button stays hidden until the page is reloaded [Requirements 2.4, 2.5, 7.1, 7.2, 7.7, 7.8].
- **D-5: Order of checks for a spoken result. Decided (approved).** Nothing is submitted when the game is not ready; at a file-name prompt the message is `TYPE THE FILE NAME.`; an empty result gives `DIDN'T CATCH THAT.`; at a yes/no prompt the yes and no words map to YES and NO; at a command prompt the magic words are tried first, then the Meta_Command block, then normal submission. Magic words are not recognised at yes/no or file-name prompts [Requirements 8.12, 9.12].
- **D-6: Meta words in the first two words are blocked. Decided (approved).** A spoken line is withheld with `TYPE THAT COMMAND; DO NOT SAY IT.` when either of its first two words is QUIT, SAVE, RESUME, SEED, WASTE or a vocabulary spelling of them (at command and yes/no prompts); a Meta word later in a longer sentence is left to the AI path, which rejects it [Requirement 9.6, 9.8].
- **D-7: Magic word details. Decided (approved).** The fourth PLUGH alias is `plug h`; a lone `fum`, `fi`, `fo`, `fee`, `fie`, `foe` or `foo` matches by exact alias; the prefixes `fee fie` and `fee fie foe` match and are submitted as two or three lines; if several Alternatives could match, the first Alternative that gives any Magic_Match wins, even over an exact classic command [Requirements 10.3, 10.8, 11.2, 11.9].
- **D-8: Hint text and where it fires. Decided (approved).** The deflection hint is the fixed line `SAY IT ALOUD. HOLD THE MIC OR ALT+M. TYPE XYZZY AGAIN IF YOU MUST.`, and it fires on the first typed XYZZY of a game even in a room where XYZZY would do nothing [Requirements 12.2, 12.3, 12.4].
- **D-11: Headers. Decided (approved).** The only header change is `Permissions-Policy: microphone=(self)`; no other policy directives are added, and `check:dist` enforces Requirements 15.1 to 15.5 on `dist/_headers`. If the deployed-site check finds the headers block recognition, they change in a follow-up [Requirements 15, 16.6].
- **D-13: No spoken announcement when listening starts. Decided (approved).** The screen reader is not told `Listening`, because it could be captured by the microphone; listening is shown by `LISTENING...` and `aria-pressed`. `Heard: ...` and the calm messages are announced after the session [Requirements 6.7, 17.7].
- **D-14: Slow permission answer. Decided (approved).** If the player takes more than about 13 seconds to answer the browser permission prompt, the start-confirmation timer ends the session with `VOICE TROUBLE. TYPE INSTEAD.` and counts it as an `other` error; this is checked on real devices [Requirements 5.12, 16.8].
